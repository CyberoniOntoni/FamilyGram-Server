# API Layer 228 upgrade plan

**Status:** planned (not complete)  
**Current production layer:** **224** (`Layers.LayerLatest`)  
**Target:** **228** (tdesktop / tdlib / tgscheme)  
**Stretch:** multi-layer **224–228** (clients may negotiate any layer in range)

## Why this is not a one-commit change

| Component | Scale today |
|-----------|-------------|
| C# TL schema entities | ~3,100 auto-generated `.cs` files |
| Messenger handlers | ~795 |
| Live server build | `0.38.224.x` → advertises **layer 224** |
| FamilyGram Web gramjs | TL close to 227–228; still forced toward **224** via `familygramTlCompat` |

Layer **224 → 228** (schema.jppgr.am):

- **~116 added** constructors/methods (communities, ephemeral, aicompose, rich messages, web browser settings, …)
- **~36 changed** constructors (including **message**, **channel**, **channelFull**, **messages.sendMessage**, **messages.editMessage**, **draftMessage**, **poll**, …)

Bumping `LayerLatest` to 228 **without** regenerating schema and dual-registering constructors will **break** deserialization for real 228 clients and can break existing 224 clients.

Upstream open-source MyTelegram latest public tag is still **layer 224** (`v0.40.224.502`). Full multi-layer through 227+ is typically a Pro / long-running track.

## Phase plan

### Phase 0 — Inventory (done)

- Diff 224→228 captured from https://schema.jppgr.am  
- Critical ID changes identified (e.g. `message#3ae56482` → `message#7600b9d3`, `messages.sendMessage#545cd15a` → `#fef48f62`)  
- Web already has many 228-shaped types; server LatestLayer is 224  
- Alias pattern exists: `SerializerObjectMappings.RegisterLegacyConstructorAliases`

### Phase 1 — Schema generation pipeline

1. Vendor layer 228 `api.tl` (from tdesktop / tdlib).  
2. Restore or reimplement **TL → C# codegen** used for `MyTelegram.Schema` (`// <auto-generated />`).  
3. Generate LatestLayer = 228 entities.  
4. Keep layer-224 entity copies under `Layer224/` (or flag-compatible aliases where bit-compatible).  
5. Unit tests: serialize/deserialize golden fixtures for message, user, channel, sendMessage at 224 and 228.

### Phase 2 — Request dual-registration

1. Register **both** constructor IDs for changed methods (224 + 228) on the same handlers where payload is flag-compatible.  
2. For non-compatible methods (e.g. `messages.importChatInvite`, `channels.joinChannel` return type changes), add dedicated Layer228 request types + adapters.  
3. Expand `ObjectIdConsts` / handler maps.

### Phase 3 — Response layering

1. `Layers.LayerLatest = 228`.  
2. Implement `ILayeredService` converters so layer **224–227** clients still receive down-converted constructors (message, channel, drafts, …).  
3. `help.getConfig` / init path reports supported min/max layer correctly.

### Phase 4 — New APIs (stubs then real)

New namespaces can start as `METHOD_NOT_IMPLEMENTED` stubs, then implement as needed:

- `communities.*`  
- `ephemeral.*`  
- `aicompose.*`  
- `account.*WebBrowser*`  
- rich message / compose extensions  

### Phase 5 — Clients

1. FamilyGram Web: `LAYER = 228`, drop forced 224-only `familygramTlCompat` patches once server is dual-capable.  
2. Refresh `api.tl` / gramjs codegen from layer 228.  
3. Desktop / Android / iOS: set build layer 228 against the same server.

### Phase 6 — Ship

1. CI docker tags `0.xx.228.y`.  
2. Staging: login, send message, media, calls, history, bots.  
3. Production pull on LXC; keep ability to pin `224` images until validated.

## Acceptance criteria

- [ ] Client `invokeWithLayer 228` completes `initConnection` + `help.getConfig` without constructor errors  
- [ ] Client `invokeWithLayer 224` still works (multi-layer)  
- [ ] `messages.sendMessage` works for both constructor IDs  
- [ ] History returns messages parseable by a 228 client (`message#7600b9d3` or layered equivalent)  
- [ ] Calls / file upload / auth regression suite green  
- [ ] README badge: API Layer 228 + multi-layer 224–228  

## Effort estimate

| Track | Estimate |
|-------|----------|
| Schema codegen + regenerate Latest | 3–7 days |
| Dual-register + layered responses | 1–2 weeks |
| New method stubs + critical handlers | 1–2 weeks |
| Client alignment + QA | 3–7 days |

**Total:** on the order of **several engineer-weeks**, not a single deploy.

## Do not do

- Do **not** only set `LayerLatest = 228` and redeploy production.  
- Do **not** force Web to layer 228 while the server still only speaks 224 Latest without dual-ID support.

## Immediate next engineering action

1. Implement / restore TL codegen for `MyTelegram.Schema`.  
2. Generate 228 LatestLayer from tdesktop `api.tl` (`// LAYER 228`).  
3. Alias 224 constructor IDs that are bit-compatible.  
4. Dual-register `messages.sendMessage` and `TMessage`.  
5. Only then flip `Layers.LayerLatest` to 228 and bump Web `LAYER`.
